Week 2 · Day 10

Training on real StS2 with SpireZero

Everything so far was the mini fight. This lesson walks the same loop through the real env: what the observation needs to become before a net can use it, how the mask enters the policy, what reward to give and what goes wrong when you get clever, how to order the fights, and how much compute a run takes.

1. The env you already have

After cargo build --profile ffi -p sts2-ffi, Python gets a batch of N fights behind one object:

from sts2 import Sts2PufferEnv
env = Sts2PufferEnv(num_envs=256, threads=4)   # 256 fights, 4 engine threads
obs, _ = env.reset()                           # uint8, shape (256, 972), engine memory, zero copy
mask = env.action_masks                        # bool,  shape (256, 140)
obs, reward, done, trunc, info = env.step(actions)   # actions: int per env, must be masked-legal

Each env is one fight from a start corpus (real Act 1 positions harvested from greedy runs: deck, relics, HP, encounter, RNG streams). When a fight ends the env resets to the next start by itself. reward is +1 / −1 / 0, exactly the mini fight's. An illegal action raises; nothing is applied. The static part of the observation (deck, relics, belt) is in env.batch.static_obs, rewritten at each reset.

2. From 972 bytes to features

Day 8 said a net generalizes only along directions its inputs make easy. Raw bytes divided by 255 technically work and are a fine first experiment, but they hide structure a net has to rediscover: a card id is a category, not a magnitude; HP matters as a fraction of max; a power's amount means nothing without its kind. The table is a reasonable featuriser for a second experiment. The offsets are day 2's.

Two structural points. First, the action space is aligned with the hand slots: a policy head that scores "play hand slot h" should see hand slot h's features, not a flattened blob. Index arithmetic in the net mirrors action.rs. Second, the vocab ids are append-only, so your embedding tables stay valid when the engine gains cards; pass vocab_hash= to the env to refuse a mismatched build.

3. The mask in the policy

logits = head(features)                             # (N, 140)
logits = logits.masked_fill(~mask, -1e9)            # illegal → probability 0
dist = torch.distributions.Categorical(logits=logits)
action = dist.sample()                              # always legal
logp = dist.log_prob(action); entropy = dist.entropy()

Mask in the logits, before the softmax, in both rollout and update. If you mask only at sampling time the policy gradient will spend capacity learning not to pick illegal actions, and the entropy term will count them. Keep the 140-wide layout even though most cells are usually dark (day 2): the net learns that hand slot 7 is rarely legal, and that is fine.

4. Reward: sparse, shaped, and hacked

+1/−1 is honest and hard: the signal arrives once per fight after 20–40 decisions. Shaping adds intermediate rewards to help, and it is the single easiest way to train an agent to do the wrong thing well. Try it on the mini fight.

Expected pattern: "+ per damage dealt" makes a berserker (damage is paid now, death is paid later and discounted); "− per HP lost" makes a turtle that can lose slowly; the HP bonus on a win is the safest of the shaped rewards because it only pays when the real objective is met; the turn penalty speeds things up at a cost. Rules of thumb for the real game: start sparse; if you shape, make it a small fraction of the terminal reward and tie it to things that are consequences of winning (HP left, potions kept), not proxies for it (damage dealt); and measure the thing you actually care about separately from the reward.

For whole runs (stage 9's run env) the sparse reward is already there (+1 victory, −1 otherwise, with the floor reached in infos); a per-floor shaping is the obvious next step, and the same warning applies twice as hard, because the agent gets to choose its own fights.

5. Which fights, in what order

  • Curriculum. The start corpus mixes trivial fights with Act 1 elites. A random policy already wins 34% of Act 1 starts, so the early signal is there. Sort starts by the random (or greedy) policy's win rate and feed the easy half first, then widen. Measure on the full corpus always.
  • Per-character. Five characters share one observation layout and one action space; a single net can learn all five (the character is in the static part), but training on one first makes debugging simpler.
  • Fights, then runs. The fight env (stage 7) trains the combat policy. The run env (stage 9) then plays whole runs, either with the agent making every decision or with combat="greedy" so it only learns the map, shop and reward choices at first. Hybrid modes exist so the two policies can be developed separately and combined.
  • Self-play does not apply: no opponent adapts. Its cousin, evaluating against fixed references (random, greedy, your previous checkpoints) on a fixed seed set, is what keeps progress honest.

Measured points from docs/perf.md: Rust through the ABI 483k steps/s per core, Python with the numpy random policy 310k (64 envs) to 349k (256 envs), the in-process fight env 798k. Random play averages about 23 actions per fight; a competent agent plays longer. Atari agents typically need 10M–200M steps; AlphaStar-scale efforts, billions.

The honest reading: with the engine this fast, the environment stops being the bottleneck almost immediately. A mid-size net evaluated on a GPU in batches of a few thousand observations tops out well below a million steps a second, and that is before PPO's update epochs. That changes what to optimise next: batch size, a model small enough to keep up, and keeping the GPU fed, not more engine speed. The engine's job was to make this the problem, and it has done it.

The math, gently

Potential-based shaping is the one kind of shaping guaranteed not to change the optimal policy: add F(s, s′) = γΦ(s′) − Φ(s) for any function Φ of the state. "−0.03 per HP lost" is of that form with Φ(s) = 0.03 · HP(s) (and γ = 1), which is why it is less harmful than "per damage dealt" (which is not a potential: it depends on what the enemy lost, and sums to a different total along different paths to the same win). Even a potential-based term changes what is learned quickly, so the toy still shows a turtle.

Sample budget. PPO iteration cost ≈ N·T env steps + E·(N·T/B) gradient steps on minibatches of B. With N = 256, T = 128, E = 4, B = 4096: 32,768 env steps (≈0.1 s at 300k steps/s) and 32 gradient steps per iteration. The gradient steps dominate as soon as the model has more than a few million parameters.
