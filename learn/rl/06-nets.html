Week 2 · Day 8

Why tables break, and how neural nets fill the gaps

The exact-state table in day 6 had twenty thousand rows for two card types and one enemy. The real game's observation is 972 bytes. No table can hold it, and worse, no table can learn anything about a state it has never visited. Intuition only in this lesson; no gradients yet.

The idea

A table treats every state as unrelated to every other. "HP 12 vs Worm 20" and "HP 13 vs Worm 20" are separate rows; learning one tells it nothing about the other. You know they are nearly the same situation. A function approximator encodes that knowledge: instead of a row per state it holds a formula from observation to value (or to action probabilities), with a few thousand to a few million adjustable numbers (parameters). Training adjusts the parameters so the formula fits the states it saw. Nearby states then get nearby outputs for free. That's generalization, and a neural network is the function approximator that turned out to be flexible enough for almost anything.

The trade: tables are exact but can't generalize; nets generalize but are approximate, and a change that fixes one state can nudge others. Everything in deep RL is about living with that trade.

Give it the same information as 972 raw bytes and it needs more capacity, more data and a sensible input encoding, which is why day 10 spends time on featurising the observation.

What a network is, in one paragraph

A layer takes a vector, multiplies it by a matrix of parameters, adds a vector of parameters, and squashes each number through a simple nonlinear function. Stack a few layers and you get a function that can bend to fit almost any shape. Training is: measure how wrong the output is (the loss), compute which direction each parameter should move to reduce it (the gradient, by backpropagation, which is just the chain rule applied efficiently), and move each parameter a small step that way (gradient descent). Repeat a million times. Libraries like torch do the gradient part for you; what you choose is the shape of the net, the loss, and the data.

For RL the two nets you will meet are the policy (observation in, action probabilities out) and the value or critic (observation in, V(s) out). Day 9 is about how to train the first one when there is no "correct answer" to compare against, only rewards.

Where this lives in SpireZero
  • Card, relic, power and monster kinds are small integer ids from crates/sts2-rl/vocab/. In a net those become embeddings: a learned vector per id, so "Strike" and "Twin Strike" can end up near each other. Append-only ids (see crates/sts2-rl/src/vocab.rs) are what keeps a trained embedding table valid across engine builds.
  • The observation is written in the engine as integers and featurised in Python. python/sts2/env.py exposes the raw bytes as a uint8 Box space; the net's input layer is where the bytes become HP fractions, embeddings and so on.
  • There is no network code in the repo yet. That is deliberate: the engine and env are the hard, finished part; the model is a Python experiment that can change weekly.
The math, gently

A two-layer network with parameters θ = (W1, b1, W2, b2):

fθ(x) = W2 · tanh(W1 x + b1) + b2

Fitting values: minimise the mean squared error over sampled states, L(θ) = mean (fθ(s) − G(s))2, by θ ← θ − η ∇θL. The toy above does exactly this, with plain gradient descent written out by hand in about 40 lines (see the page source).

Deep Q-learning (DQN) plugs fθ in for the table and uses the day 6 target, with two stabilisers: a replay buffer of past transitions, and a slowly-updated copy of the net for computing targets. We won't use DQN for SpireZero (policy-gradient methods handle masks and large action spaces more gracefully), but the idea carries over unchanged.
