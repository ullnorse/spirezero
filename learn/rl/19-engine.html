Week 4 · Day 19

The engine side

Everything the trainer assumes about the env is a promise made in three Rust files. Today reads those promises, checks them from Python over thousands of steps, sees what an illegal action does, and measures how the batch and the thread count set the steps per second the trainer can count on.

The idea

The mask is not a hint; it is derived from the engine's own legal-action list, so an index with a bit set is accepted and one without is refused before anything is applied. The observation is a fixed-layout view of the state with saturating fields. The stats after each step reconcile with the done and won flags. A trainer may assume exactly these things, and an audit that checks them after every step is cheap enough to leave on.

What the mask promises

  • Derived, never computed beside. Combat::legal_actions_into lists the legal actions; action.rs sets one bit per listed action and records its list position, so decoding an index reads the engine's own action back. A listed action with no index (an eighth enemy, an eleventh option) gets no bit and is counted in StepStats.unmapped.
  • Never empty. A finished fight is reset before you see its mask, so every live env has at least one legal action. Only a batch that ran out of starts (a sequential corpus) has empty masks, and the default source never does.
  • Slot-consistent. A legal play index names a hand slot below the hand size; a legal potion index a belt slot below six; End turn and Done are never legal together.
  • Enforced. An action without a bit raises Sts2Error (code −3) from step, and nothing is applied to any env of the batch. The exercise checks the observation is byte-for-byte unchanged.

What the buffers promise

obs, static_obs, masks, done and won are views on engine memory, rewritten in place by every step. Copy what you keep (the rollout does, by turning each step's observation into a tensor). The header's fields saturate rather than wrap: HP between 0 and max HP, block and energy non-negative, at most ten cards in hand, a status byte in 0..4. invariants.rs checks the same things plus pile conservation after every fuzzed step; the exercise's check_header is the Python half of it.

After a step, stats() says what happened: actions applied, episodes ended and won, capped at 10,000 actions, reset. Ended equals the number of done flags, won equals the won flags, reset equals ended as long as starts remain. A trainer's episode and win counters should reconcile with these every iteration; a drift is a bug on one side or the other.

Threads and batch

One call to step steps every env; threads=k splits the batch across k engine threads inside that call. The episodes are handed out in env order after the batch has stepped, so trajectories do not depend on k and the evaluation protocol holds for any thread count.

Toy · steps per second, measured by the exercise

Random play on 256 envs: every added thread costs throughput. A random policy's step is about 3 µs of engine work per env; the fork and join per call costs more than that, and the Python side (unpacking masks, drawing actions) is single-threaded whatever k is. At 1,024 envs the threads break even, and the single-threaded figure drops as the batch stops fitting in cache. Threads pay when the step is heavier than the sync: the run env with the greedy resolver (hundreds of µs per decision), a corpus of long fights, or a batch big enough per call. Measure on your own machine with the exercise's bench, then size the batch so the net, not the env, is the bottleneck, as day 10's calculator showed.

Where this lives in SpireZero
  • crates/sts2-rl/src/envs.rs: Envs::step_with (the illegal check before anything is applied, the per-env reset and the stats), MAX_EPISODE_ACTIONS, each_env for the thread split.
  • crates/sts2-rl/src/action.rs: the index arithmetic and IndexMask::fill, where the list becomes bits; crates/sts2-rl/src/invariants.rs: what the fuzzer checks after every step.
  • crates/sts2-ffi/include/sts2.h: the C ABI (error codes, sts2_envs_stats, the layout struct) that python/sts2/ffi.py wraps.
  • docs/perf.md: the measured steps per second for every build and workload, with the method.
